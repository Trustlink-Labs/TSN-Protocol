---
title: "Use a Private TIN in a TSN Payment App"
sidebarTitle: "Private TINs"
description: "Build a privacy-aware payment experience with the TSN SDK without exposing TIN secrets to application servers or settlement operators."
---

TSN applications use private-by-default TINs. The owner supplies a phone
number as private lookup material, but the phone number is not published as a
TIN field on chain. A real phone-ownership verification step must complete
before the creation authorization is signed. The Solana program assigns the
10-digit TIN during the creation transaction, so an application must not ask a
creator to type an assigned TIN before creation.

The TSN SDK produces the commitment and encrypted envelope needed for
settlement coordination. The Node, Receiver, and generic Cranker receive
authenticated protocol data, not a plaintext phone number, TIN, or identity.

## Application boundary

```text
Payment UI -> @trustlink/tsn-sdk -> TSN services -> generic Cranker
```

The application integrates through `@trustlink/tsn-sdk`. It does not import
TCAP or TIN program clients directly, derive settlement PDAs, or assemble raw
settlement instructions. Those responsibilities remain behind the SDK and
service boundaries.

## Creation sequence

The owner-facing flow is:

1. Normalize and verify ownership of the phone number with the configured verification provider.
2. Prepare the encrypted identity and signed creation authorization locally.
3. Submit the creation operation through the TSN service boundary.
4. Let the Solana program assign the TIN during finalization.
5. Show the assigned TIN to the owner only after the finalized on-chain record is read.

The phone number is a lookup secret, not the display name. Do not log it or
send it to a Cranker. The current prototype UI intentionally blocks the create
button until a real verification provider is connected; it does not simulate
OTP ownership.

## Prepare private identity material locally after issuance

The SDK creates an encrypted identity envelope and its lookup commitment in
the owner-controlled application boundary. The finalized TIN is never sent to
the Node as a plaintext lookup secret.

```ts
import { createTinV1IdentityEnvelope } from "@trustlink/tsn-sdk/tins";

const identity = await createTinV1IdentityEnvelope({
  tin: issuedTin,
  displayName: userDisplayName,
});

const creationData = {
  tin: userTin,
  lookupCommitment: Buffer.from(identity.lookupCommitment).toString("hex"),
  encryptedIdentityEnvelope: Buffer.from(identity.encryptedIdentityEnvelope).toString("base64"),
};
```

Keep the phone lookup secret and assigned TIN under the owner's control. Do
not log either value, place either value in a Cranker payload, or include
either value in analytics events.

The application submits an owner-authorized creation request through the TSN
service boundary and displays the returned operation status. It does not call
a direct `createTin` program method.

## Resolve a TIN and prepare a payment

Resolve a TIN with the SDK after the owner authorizes local disclosure, then
use the returned route commitment to prepare a payment authorization.

```ts
import {
  createPaymentAuthorization,
  resolveTinRoute,
} from "@trustlink/tsn-sdk";

const identity = await resolveTinRoute({
  tin: recipientTin,
  rpcUrl: TSN_RPC_URL,
  programId: TIN_PROGRAM_ID,
});

const authorization = createPaymentAuthorization({
  senderWallet: wallet.publicKey.toBase58(),
  senderIdentity: `wallet:${wallet.publicKey.toBase58()}`,
  receiverIdentity: `tin:${recipientTin}`,
  recipientRouteCommitment: identity.tcapRelationshipCommitment,
  recipientRouteVersion: identity.tcapRouteVersion,
  tokenMintAddress: settlementMint,
  amount,
  senderFeeAmount,
  totalTokenRequiredUi: amount + senderFeeAmount,
  fundingMode: "wallet_only_v2",
});
```

The wallet signs the authorization required by the SDK-generated intent. The
Node validates the request and route, while the generic Cranker submits only
the authorized protocol operation.

## Build a wallet-to-wallet transfer

Use the SDK to construct the unsigned transaction. The connected wallet signs
it; no private key is passed to the SDK or Node.

```ts
import { buildTsnSplTokenTransferTransaction } from "@trustlink/tsn-sdk";
import { Transaction } from "@solana/web3.js";

const unsigned = await buildTsnSplTokenTransferTransaction({
  senderWallet: wallet.publicKey.toBase58(),
  recipientWallet,
  tokenMintAddress: settlementMint,
  amountUi: "1.00",
  tokenDecimals: 6,
  rpcUrl: TSN_RPC_URL,
});

await wallet.signTransaction(
  Transaction.from(Buffer.from(unsigned.transactionBase64, "base64")),
);
```

For a TIN payment, use `createPaymentAuthorization` and
`buildPaymentAuthorizationIntentRequest` from the SDK instead. The SDK is the
application interface; the TSN services coordinate settlement underneath it.
